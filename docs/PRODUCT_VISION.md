# Mallok 产品愿景

- 产品方向：0.1 基线
- 文档日期：2026-08-28
- 首个产品版本：0.1
- 计划开源仓库：`JasonYv/mallok`
- 计划许可证：MIT（待 `JasonYv` 最终确认，见 §10）

## 1. 一句话定义

**Mallok 是一个开源、Cloudflare 原生的内容网站产品：内容以 Markdown 存在 D1 中，改完即时生效，不需要构建，不需要服务器，内容随时可以带走。**

## 2. 战略判断

内容网站今天有两条路，各有一个结构性缺陷：

- **CMS 路线（WordPress、Ghost）**：编辑体验好、改完即生效、有主题和插件生态。代价是你得养一台服务器、一个数据库、一套持续的安全更新，性能还要靠一层层缓存插件去救。
- **静态生成路线（Astro、Hugo、Eleventy）**：性能和输出质量极好、部署便宜。代价是内容变成了源码仓库的一部分——改一个错别字要提交、跑 CI、等构建、重新部署，而且非技术的人根本进不来。

Mallok 认为这两个代价都不是必须付的。Cloudflare 的 Worker + D1 + R2 让「数据库里的内容」和「边缘直出的静态字节」第一次可以是同一件事。

> WordPress 的编辑体验，边缘网络的性能，开源且不锁定你的内容。

对照关系要说清楚：**Mallok 的直接竞品是 WordPress 和 Ghost**，Astro 是性能与输出质量上的参照物，不是要打赢的对象。用户从 Astro 迁到 Mallok 的理由是「不想再为改一句话跑一次构建」；从 WordPress 迁到 Mallok 的理由是「不想再养服务器和补安全漏洞」。

## 3. 核心用户

### 3.1 首要用户

- 需要一个博客、文档站或公司官网，愿意接受一次技术性部署，但不愿长期运维的开发者与技术团队；
- 从 WordPress 出走、受够了主机、插件冲突和安全更新的站点所有者；
- 用 Astro/Hugo 建了站，但受不了「改内容要走 Git 和 CI」的作者。

### 3.2 次要用户

- 为客户交付内容站、希望交付后客户能自行更新的服务商与工作室；
- 部署后只负责写内容、不接触基础设施的编辑与运营；
- 为 Mallok 写主题和插件的设计者与开发者。

### 3.3 不服务的用户

Mallok 0.1 不面向电商交易、会员与权限体系、复杂表单流程、后台管理系统，以及需要自由编写服务端业务逻辑的应用。这类需求应使用通用框架，不应把 Mallok 扩张成通用框架。

## 4. 产品模型

部署是一次性动作。部署完成后，日常只有四个对象：

1. **内容**：页面、文章、媒体。
2. **主题**：网站长什么样，以及主题开放的配置项。
3. **设置**：站点名称、导航、域名、语言、SEO 默认值。
4. **插件**：扩展能力。这是高级层，普通使用不需要接触。

底层仍然有 Worker、D1、R2、缓存、schema 迁移和版本，但后台界面不得要求用户理解它们。任何新功能必须归入以上四个对象；归不进去时，优先判断它是不是内部复杂度，而不是增加第五个顶级概念。

## 5. 产品承诺

### 5.1 改完即时生效，不需要构建

保存一篇文章 = 写一行 D1 + 精准清除对应缓存。没有构建队列、没有 CI、没有重新部署、没有「等两分钟看看生效没有」。**这是 Mallok 相对所有静态生成器最核心的差异，任何设计都不得牺牲它。**

### 5.2 内容是标准 Markdown，随时可以带走

D1 中存的是 Markdown 原文加 YAML frontmatter，不是渲染后的 HTML，也不是私有结构。一次导出就得到一个普通的 `.md` 文件目录，可以直接喂给 Astro、Hugo、Obsidian 或任何别的工具。**不锁定不是营销话术，是可执行的导出功能，且必须有测试覆盖往返一致性。**

### 5.3 部署到你自己的 Cloudflare 账号

Mallok 不托管任何东西。站点、数据库、图片、域名全部在用户自己的 Cloudflare 账号下，Mallok 拿不到也管不着。0.1 没有 Mallok 账号体系，没有计费，没有多租户控制面。

### 5.4 访客页面默认零客户端 JavaScript

后台的复杂度不进入访客页面。官方主题默认输出语义化 HTML 和 CSS，客户端 JavaScript 为 0 B；需要交互时由主题或插件显式增加，并说明代价。

### 5.5 换主题不动内容

主题是声明式的，运行时加载。换主题只改一个设置字段，即时生效，不迁移内容、不改变内容 ID，默认不改变公开 URL。主题里没有任意 JavaScript，装一个陌生主题不等于在自己站上跑陌生人的代码。

### 5.6 插件的边界是诚实的

插件是真正的 JavaScript 代码，通过声明式的钩子介入。它在构建期打包进 Worker，因此**安装或更新插件需要重新部署一次**——这一点必须在界面上讲明白，不能为了「一键」假装它是热插拔的。插件跑在用户自己的账号里，风险边界与 WordPress 插件一致，产品要如实说明而不是掩盖。

### 5.7 本地和线上是同一套东西

后台可以跑在本地 localhost，也可以部署在 Cloudflare 上，是同一份代码、同一套 API。CLI 是第三个入口，同样调这套 API。三者之间不存在能力差。

### 5.8 开源，且社区能真正参与

主题和插件有公开、文档化、有版本的契约，第三方写的和官方写的用同一套机制。没有只有官方能用的私有接口。

## 6. 竞争定位

| 维度 | WordPress | Astro | Mallok |
| --- | --- | --- | --- |
| 内容存哪 | 数据库 | Git 里的文件 | D1 里的 Markdown |
| 改内容后 | 即时生效 | 提交 → CI → 构建 → 部署 | 即时生效 |
| 内容可携带性 | 导出格式私有，迁移痛苦 | 本来就是 `.md`，最好 | 一键导出成标准 `.md` |
| 运维负担 | 主机、数据库、安全更新 | 无（静态） | 无（Cloudflare 托管） |
| 非技术者能否更新 | 能 | 基本不能 | 能 |
| 首次部署难度 | 中（要买主机） | 中（要会 Git/CI） | 中（要有 CF 账号，一次引导） |
| 生态 | 极大 | 大 | 从零开始 —— **这是 0.1 最大的短板，必须承认** |

胜负标准不是 benchmark 分数，是：WordPress 用户愿不愿意搬过来，Astro 用户愿不愿意为「不用构建」换掉组件自由度。

## 7. 0.1 成功画面

一个此前没用过 Mallok 的开发者可以：

1. 跑一次引导式部署，把 Mallok 装进自己的 Cloudflare 账号；
2. 打开后台，得到一个已经能访问的站点；
3. 写一篇文章，保存，几秒内在公开 URL 上看到它；
4. 换一个主题，刷新即生效，文章 URL 不变；
5. 把已有的 Markdown 文件夹导入进来；
6. 用 CLI 从本地提交一篇 Markdown；
7. 一键把全部内容导出成 `.md`，确认自己随时能走；
8. 绑定自己的域名，站点在自定义域上正常服务且缓存生效。

只完成渲染内核、只完成 CLI、或只有本地能跑，都不等于完成 0.1。

## 8. 非目标

- 不做 Mallok 托管服务、账号体系、计费或多租户（这是 1.0 之后的方向，不属于 0.1）；
- 不做电商、会员、评论、表单提交等需要写业务逻辑的功能，这些留给插件；
- 不做在线多人协作编辑；
- 不成为 Astro/Next.js/WordPress 的兼容层，也不实现 PHP 或 WordPress 主题格式；
- 不要求用户理解 Worker、D1、R2、缓存或 schema 迁移；
- 不用隐藏费用、账号归属、失败状态或数据删除影响来伪造「一键」。

## 9. 已知风险

必须写在愿景里，因为它们会决定产品成败：

1. **Free 计划的 10 ms CPU 限制**。请求时渲染 Markdown 加模板很容易超出。缓存命中的路径必须极廉价，冷渲染必须做过预算，且产品要如实告知 Free 计划的适用边界。见 [ARCHITECTURE.md](ARCHITECTURE.md)。
2. **Cache API 在 `.workers.dev` 子域上不生效**，意味着「必须绑自定义域」可能是硬前提，会抬高首次部署门槛。这一条必须在实现前用真实 spike 验证并写进部署引导。
3. **生态从零开始**。0.1 只有官方主题和极少插件，短期打不过 WordPress 的生态。策略是先赢「不用运维 + 不用构建 + 不锁定」这三点，生态靠时间。
4. **依赖单一云厂商**。Mallok 0.1 与 Cloudflare 强绑定。缓解手段是内容随时可导出，而不是假装支持多云。
