# Mallok 产品战略与演进路线

- 状态：0.1 战略基线
- 日期：2026-08-27
- 计划品牌入口：`mallok.dev`
- 计划开源仓库：`JasonYv/mallok`

## 1. Mallok 要创造的不是另一种框架

Mallok 的品类不是 “static site generator”，而是 **content-site appliance**：一个安装后即可创建、编辑、发布和长期维护内容网站的本地产品。

Astro 的核心单位是项目和组件；Mallok 的核心单位是站点数据。二者服务不同的默认用户：

- 需要自由编程、组件组合和应用逻辑：使用通用框架；
- 需要博客、知识库、内容站或中小企业官网：Mallok 直接交付完整产品。

产品边界可以用一句话判断：

> 需要写组件时，Mallok 不是正确工具；只需要拥有并维护一个内容网站时，不应该再被迫建立前端工程。

## 2. 颠覆性来自五个结构性取舍

### 2.1 站点是数据，不是源码仓库

每个站点只有设置、Markdown、媒体和模板选择。没有每站点依赖、构建脚本、框架配置和 lockfile。Mallok 升级的是一个产品，不是逐个升级用户站点工程。

### 2.2 Studio 是产品本体

创建、编辑、预览、发布和恢复都有可视路径。CLI 只服务批量与自动化，不能成为 Studio 的隐藏依赖。产品是否成功由非开发者任务完成率判断，不由 CLI demo 判断。

### 2.3 模板是受约束设计，不是可执行代码

0.1 只提供三个高质量官方模板和少量安全设计 token。主动放弃任意组件和 JavaScript 主题，换取模板切换不迁移内容、没有依赖冲突和可预测升级。

### 2.4 一个 compiler、一个 PublishBundle

本地 preview、静态导出和 Cloudflare 发布共享内容与模板语义。公开 Worker 只分发已渲染结果，不在请求时运行站点代码。维护者只需守住一条编译和安全边界。

### 2.5 发布是产品动作，不是部署教程

用户只看到变化、目标网址、当前结果和恢复入口。OAuth、D1、R2、Worker、迁移和并发控制由产品吸收；普通用户不选择运行模式或复制 token。

## 3. 首个市场楔子

0.1 只服务三类站点：

| 场景 | 官方模板 | 典型用户 | 核心价值 |
| --- | --- | --- | --- |
| 博客/新闻/长文 | Journal | 独立作者、顾问、媒体小团队 | 写完即可发布，排版稳定 |
| 知识库/文档 | Docs | 小团队、开源项目、服务商 | 导航明确，无需搭文档工程 |
| 企业/产品官网 | Company | 小企业、工作室、外贸团队 | 自己维护，不再每次找开发者 |

这三类场景共享页面、文章、图片、导航和 SEO，能用一个内容模型覆盖。电商、会员、复杂表单、任意交互和 Web 应用不属于首个楔子。

## 4. 产品阶梯

### 4.1 0.1：证明产品成立

- macOS Apple Silicon 自包含 Studio；
- 三个官方模板；
- 可视编辑与 Markdown 导入导出；
- 本地预览、静态导出；
- 用户自有 Cloudflare 账号的浏览器 OAuth 发布；
- 日常更新、状态确认和恢复上一版本；
- 同版本高级 CLI。

0.1 的目标是证明“非开发者可以独立完成内容站闭环”，不是一次覆盖所有站点类型。

### 4.2 0.5：扩大可迁移性和覆盖面

- WordPress、Astro 和通用 Markdown 导入器；
- Windows 发行版；
- 更多受约束官方模板；
- 高级媒体库、多宽度图片、手工裁剪、动画/视频优化、站内搜索和多语言；
- 更完整的本地发布历史与站点诊断。

### 4.3 1.0：消除最后一个云平台门槛

真正面向最广泛非技术用户时，默认发布应升级为可选的 **Mallok Cloud**：用户只登录 Mallok、选择域名并发布，不需要先拥有或理解 Cloudflare 账号。用户自有 Cloudflare 与静态导出继续作为高级、可退出路径。

这是长期产品方向，不属于 0.1。把它提前会同时引入账号、计费、多租户、滥用防护、数据责任、支持与在线运维，足以吞没对核心产品的验证。

## 5. 开源与商业模型假设

以下是商业假设，不是已经批准的价格或许可证决定：

- 开源：Studio、CLI、项目格式、compiler、三个基础模板和自托管 Cloudflare 路径；
- 付费候选：Mallok Cloud 托管、自定义域名引导、托管备份/同步、团队协作、服务商工作台和高级模板包；
- 永久可退出：Markdown、媒体、项目备份和静态导出不因付费状态被锁定；
- 不用插件抽成作为早期商业核心，避免为了市场规模重新制造组件生态和兼容负担。

许可证必须在公开仓库前由 `JasonYv` 单独决定。若希望云服务可商业化同时接受社区贡献，需要在宽松许可证、商标政策和 hosted-service 竞争之间明确取舍，不能由实现者默认选择。

## 6. 真正的护城河

Mallok 的护城河不应是私有文件格式或组件数量，而是：

1. 非开发者从安装到发布的完成率；
2. 数据型站点格式带来的迁移和长期可维护性；
3. 同一 compiler/bundle 在本地、静态和托管间的一致结果；
4. 经过大量真实内容验证的模板、编辑器和导入器；
5. 失败状态、恢复和升级体验形成的信任；
6. 公开、可复现的“更少步骤、更少概念、更少维护”数据。

别人可以复制命令或界面，但很难快速复制大量真实站点迁移、失败恢复和长期升级证据。

## 7. 发布与增长路径

### 7.1 0.1 发布前

- 用 10 名目标用户验证创建、预览、首次发布、更新和恢复；
- 用三个真实示例站而不是 lorem ipsum 展示 Journal、Docs、Company；
- 发布数据型项目格式和静态导出，先建立“不锁定”的信任；
- 在 `mallok.dev` 用 90 秒内演示“选模板 → 改内容 → 发布”。

### 7.2 首批获取

- GitHub 面向开发者与服务商传播开源和架构透明性；
- `mallok.dev` 面向内容所有者讲“网站不是前端工程”；
- 优先展示从 WordPress/Astro/Markdown 迁移的真实维护对比；
- 鼓励服务商交付后把 Studio 留给客户，而不是把客户绑定给维护者。

### 7.3 评价产品的北极星指标

北极星不是 star、模板数或生成速度，而是：

> 发布后 90 天，仍能由站点所有者独立完成更新且无需开发者介入的活跃站点比例。

辅助指标：首次发布完成率、发布中位时间、30/90 天维护分钟数、恢复成功率、模板切换后 URL 保留率和每站点依赖冲突数。

## 8. 反路线图

以下诱惑会让 Mallok 重新变成一个更弱的 Astro，0.1 明确拒绝：

- 为了“灵活”开放任意组件、JS、npm 主题或插件；
- 同时支持多套 compiler、SSR/SSG 模式或多个云 provider；
- 用配置项代替产品决策；
- 先做 SDK/Theme API，再等待未来补 Studio；
- 用模板数量、benchmark 或 GitHub star 替代目标用户完成率；
- 为了漂亮的一键文案隐藏费用、账号归属、失败状态或数据删除影响。

Mallok 的优势来自持续删除用户必须做的决定。任何新增能力若不能降低完成成本或维护成本，就不应进入默认产品。
