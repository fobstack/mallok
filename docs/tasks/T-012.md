## 7. CI、依赖与安全检查

- 主 CI 固定 Node `22.22.2`、pnpm `11.1.3`，兼容 CI 测当前批准的最新 Node 24；macOS/Linux 各至少一次，Windows path/type/unit best effort；
- CI 运行 lint、typecheck、coverage、build、package/import、static E2E、local D1/Worker/publish、deploy dry-run；

- 构建产物与测试日志不得持久化 token、文章草稿或本地 state。
- 创建稳定根脚本 `release:check`，聚合 `verify`、pack/license/advisory/secret/document checks 并保留每个子命令退出码；它不得包含 npm publish、Git 写操作或 Cloudflare remote/staging。

本任务批准且只批准以下 root direct dev dependencies；必须先形成仅含 package manifest/lockfile/必要注册元数据的 dependency-only diff，独立 reviewer 通过后再写功能代码：

- `playwright-core@1.62.1`（Apache-2.0）与 `@axe-core/playwright@4.13.0`、`axe-core@4.13.0`（MPL-2.0）：驱动明确提供的本机 Chromium/Chrome 做 a11y 测试；不得在 install/lifecycle 中下载浏览器；
- `secretlint@13.0.5` 与 `@secretlint/secretlint-rule-preset-recommend@13.0.5`（MIT）：扫描当前树及由项目脚本逐 blob 提供的 Git history；输出只保留 rule/path/commit，不回显命中值；
- `license-checker-rseidelsohn@4.4.2`（BSD-3-Clause）：生成生产依赖 license inventory。选择 4.4.2 是因为当前 5.x 要求 Node 24，而 Mallok 主发布基线为 Node 22。

这些依赖都不得进入 runtime package。a11y gate 要求 `MALLOK_TEST_CHROME_PATH` 指向预先安装、明确记录版本的本机浏览器；缺失即阻断 AC-NFR-13，不能自动下载或静默跳过。若负责人希望改用别的扫描器/浏览器驱动，必须先改单独 dependency gate，不得临时选择 `latest`。简单 grep 只能作补充，不能冒充完整 scan。

### 7.1 Accepted release evidence

全部 gate 对同一 clean candidate SHA 通过并经人工 reviewer 接受后，release 工具以临时文件 + fsync + rename 写唯一 gitignored evidence：`.mallok/evidence/T-012/<candidate-sha>.json`。文件必须通过 [`release-evidence.schema.json`](../schemas/release-evidence.schema.json) 和其中列出的 runtime constraints，且是无 BOM UTF-8 JSON object，至少包含：

```json
{
  "schemaVersion": "1",
  "task": "T-012",
  "status": "accepted",
  "candidateSha": "<40-or-64-lowercase-hex>",
  "sourceRepository": {
    "owner": "JasonYv",
    "name": "mallok",
    "canonicalUrl": "https://github.com/JasonYv/mallok",
    "packageRepositoryUrl": "git+https://github.com/JasonYv/mallok.git",
    "homepageUrl": "https://mallok.dev",
    "bugsUrl": "https://github.com/JasonYv/mallok/issues",
    "controlStatus": "verified",
    "verificationMethod": "authenticated-owner-confirmation",
    "verifiedAt": "2026-08-27T00:00:00.000Z",
    "verifiedBy": "reviewer@example.com"
  },
  "environment": {"node": "22.22.2", "pnpm": "11.1.3", "os": "darwin-arm64"},
  "gateResults": [{"name": "pnpm release:check", "exitCode": 0, "durationMs": 1}],
  "artifactHashes": [{"path": "<project-relative-artifact>", "sha256": "<sha256>"}],
  "networkOrigins": ["https://registry.npmjs.org"],
  "cloudflareApiOrigins": ["https://api.cloudflare.com"],
  "verifiedAt": "2026-08-27T00:00:00.000Z",
  "reviewedBy": "reviewer@example.com"
}
```

`sourceRepository` 是绑定 candidate SHA 的人工控制权 attestation：finalizer 不得从本地 remote 或公开仓库存在性自动推导 `verified`；`verifiedBy/verifiedAt` 必须分别等于顶层 `reviewedBy/verifiedAt`，该人工 reviewer 必须实际查看 authenticated owner 权限，不能把 token、cookie 或管理页截图写入 evidence。finalizer 同时核对全部 package manifest 的三个 canonical URL 与该对象逐字节一致。

schema/runtime 反例必须覆盖：缺 `sourceRepository`、owner/name/任一 URL 漂移、顶层与内层 reviewer/time 不同、package manifest URL 不同，以及仅因本地 remote 或公开 GET 成功就把 control 标为 verified；这些情况都不得生成 `status="accepted"` evidence。

所有数组去重并按 Unicode code unit 升序；origin 只能是 canonical `https://<host>[:port]`，不得含 userinfo/path/query/fragment。canonical 的可执行判定是 `new URL(value).origin === value`：scheme/host 小写、默认 443 省略，显式 decimal port 只能为 1..65535。`networkOrigins` 是本任务**实际发生**的只读网络 origin，离线运行可为空；`cloudflareApiOrigins` 是 reviewer 针对锁定 Wrangler/Cloudflare adapter 审核后供 T-013 使用的闭合 remote allowlist，MVP 固定至少含 `https://api.cloudflare.com`，T-012 自己不访问它。`artifactHashes` 覆盖所有拟交给用户/下一 gate 的 tarball和Cloudflare candidate snapshot manifests/bundle。

evidence 不包含 token、完整云 ID、正文、日志或它自己的 exact-bytes hash。T-013 将只从 candidate SHA 推导该路径并对原文件 exact bytes 计算 SHA-256；因此接受后不得原地改写。同 path 已存在且 bytes 不同必须阻断并要求新的 candidate SHA，不能覆盖。`reviewedBy` 是人工审查记录，自动化不能自行填成“accepted”。唯一 finalize 入口是 `pnpm release:evidence -- --candidate-sha <sha> --reviewed-by <human-id>`：它要求 clean HEAD 与 SHA 相同、`release:check` 同 SHA 全通过，重新计算全部 artifact hash，按 schema 规范化并验证后写文件；调用者不能传 gate status、artifact hash、origin 以伪造结果。

## 8. 性能与确定性

- 生成 `TESTING.md` 固定的 1000 篇 × 10 KiB、100 个总计 10 MiB 资源 fixture，使用 `asOf=2026-08-27T00:00:00.000Z`；
- 干净构建至少 5 次，单独报告 cold/warm、中位数、p95、Node/OS/CPU/内存；
- 10 秒是工程目标，不是对所有机器的硬承诺；
- 两次构建文件清单/hash 必须一致；
- 同时记录单文章编译 p95（目标 50ms）、local warm Worker p95（目标 100ms）、peak RSS（目标 512 MiB）、查询数和 bundle size；不用本地值冒充线上性能。
