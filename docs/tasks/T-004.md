## 1. 目标

实现 Node 文件系统上的确定性静态构建：从规范内容、Theme API 和公开资源生成首页、文章页、404、RSS、sitemap 与 assets，并通过项目内临时目录安全替换正式输出。本任务不实现用户命令、watcher、HTTP server 或 Cloudflare。

同时在 core 提前实现可复用的 Markdown 图片引用提取与 media manifest 纯验证能力。T-010 只能消费这些能力，不得再造另一套 Markdown/media 规则。

## 4. 交付范围

### 4.1 BuildWriter 与计划

- 在 core 定义最小平台端口 `BuildWriter.write(path, body)`；它只接受已经过 route/output path 校验的 POSIX 相对路径；
- Node adapter 实现目录创建、UTF-8/二进制写入和重复路径拒绝；
- 静态 build 先在内存形成按 output path 升序的完整 plan，再执行任何写入；
- generated routes、theme assets 与 public assets 发生路径冲突时失败，不设隐式覆盖优先级；
- build 生成 `BUILD.md` 第 6 节 schema `1` 的 `.mallok/build-manifest.json`，数组按 URL 排序；manifest 不复制到公开 output，也不把自身纳入 hash；
- `files` 覆盖全部 public-addressable managed output，`assets` 是其中 public/theme 的一一对应投影；测试拒绝 duplicate url/outputPath、乱序、漏项、额外项和投影字段漂移，并检查 schema 的 `x-mallok-*` runtime extensions；
- `inputHash` 精确覆盖规范 config、content artifact、theme bundle、asset、versions、`asOf` 与 target。

### 4.2 页面与资源

输出必须包含：

- `index.html`；
- `articles/<slug>/index.html`；
- `404.html`；
- `rss.xml`；
- `sitemap.xml`；
- `/assets/theme/**` 下的基础主题资源；
- 在最终 route/asset plan 上校验所有可见 Markdown 的 `/assets/...` 图片引用；缺失资源以 `CONTENT_NOT_PUBLISHABLE` 阻止正式 output 替换；
- `public` 中经过边界检查的普通文件。

生产静态构建默认排除 draft 和未来文章。`asOf` 是 build 的必填规范 UTC输入；上层 CLI 可以在命令开始时固定它。生成 HTML 不注入开发脚本。

公开资源只复制文件字节，不把 mtime、权限、inode 或主机绝对路径写入产物。拒绝 symlink、socket、device、FIFO、反斜杠、百分号和 route 冲突；枚举顺序固定。单/总 bytes、10,000 files、20,000 visited entries、32 segments、1,024 path bytes 与 255 segment bytes 的边界和各自 `+1` 反例，MIME、NFC 与保留路由严格遵守 `BUILD.md` 第 4、5 节。

### 4.3 输出边界

- 项目根、内容、theme/public、`.mallok/tmp` 和 output 都必须在操作前规范化并验证 realpath/父链；
- output 不得是项目根、文件系统根、用户主目录、内容目录、theme 目录或它们的祖先；
- 现有 output 若是 symlink/junction 或其父链越界，拒绝；
- 临时目录固定在项目 `.mallok/tmp/` 下并与 output 位于同一文件系统边界；临时随机名不得进入产物或 manifest；
- 所有 plan 写完并校验 hash 后才替换 output；按 `BUILD.md` 第 9 节执行 stage → backup → output；替换失败尽力恢复；回滚也失败时返回 `BUILD_RECOVERY_REQUIRED` 并保留两个精确路径；
- 失败只清理由本次构建创建的 stage；启动清理只允许删除 `.mallok/tmp` 下 schema 可验证、超过 24 小时且不属于当前进程的 stage；
- 测试覆盖 rename、write、cleanup 故障注入和恢复。

### 4.4 确定性

在 content、config、theme、Mallok/compiler/schema version 与 `asOf` 相同的前提下：

- 文件清单、每个文件字节和 manifest 必须一致；
- 不受 TZ、locale、文件 mtime、枚举顺序和临时目录名影响；
- 所有文本统一 UTF-8 和 LF；
- 文章与资源按稳定第二关键字排序。

### 4.5 Core media 纯函数

- 精确实现并从 `@mallok/core/media` 导出 `BUILD.md` 第 5.1 节的两个函数与五个公开类型；不得改名、增删字段或改成私有 helper。
- 从已规范化 Markdown 提取 inline/reference-style image destination 和 1-based AST 位置；代码块、inline code 与 raw HTML 中的外观文本不得误判为图片。结果按源码位置保序，不做会丢失诊断的去重。
- validator 只接受已通过 asset-manifest schema 的候选数据：HTTPS 通过且不持久化，安全 `/assets/**` 必须 exact-match；相对路径、`data:`、协议相对 URL 与 missing asset 返回规定的稳定 issue/reason。成功时返回按 URL 排序去重的 `{url}`，最多 100 项；第 101 项返回 `TOO_MANY_SITE_ASSETS`；存在任一 issue 时 references 必须为空。它不得读写文件、访问网络、上传资源或调用 D1。
- manifest 自身的 schema/重复/hash/bytes 错误由 adapter 先以 `BUILD_ASSET_INVALID` 拒绝，不能混成 `CONTENT_NOT_PUBLISHABLE`。
- manifest 结构错误不得继续内容验证；合法 manifest 的全部引用 issue 必须完整、稳定返回，不能在首个 missing asset 后隐藏其余问题。同一输入的提取和验证结果必须字节级稳定。

## 10. 停止条件

- 无法证明 output、backup 或 temp 删除目标的项目边界；
- 原子替换失败会破坏上次成功输出且无法恢复；
- 需要 shell 删除命令、管理员权限或项目外持久路径；
- 资源冲突只能通过隐式覆盖解决；
- 构建结果依赖 mtime、隐式当前时间、locale 或目录枚举顺序；
- 需要改变 Theme/Content 公共契约才能继续。
- Markdown 图片引用或 manifest 规则无法在无文件系统、无网络的 core 纯函数中表达；此时必须先升级契约，不得把第二套规则推迟到 T-010。
