## 5. 计划模型

`provision` 和 `deploy` 共享只读 `Plan` 格式：

```ts
interface DeployPlan {
  schemaVersion: "1";
  kind: "provision" | "deploy" | "migration" | "recover" | "repair" | "rollback" | "cleanup";
  environment: string;
  target: "cloudflare";
  account: {
    displayName: string;
    verification: "verified" | "unknown";
    idDigestPrefix?: string;
  };
  estimatedRemoteMutations: number;
  recoveryStrategy: "none" | "local-state" | "d1-fence" | "staging-ownership";
  hasRemoteWrites: boolean;
  hasLocalWrites: boolean;
  actions: readonly PlanAction[];
}

interface PlanAction {
  order: number;
  resourceType: "account" | "d1" | "migration" | "deploymentFence" | "worker" | "assets" | "health" | "localState";
  logicalName: string;
  action: "inspect" | "create" | "reuse" | "acquire" | "transition" | "resolve" | "apply" | "uploadVersion" | "activateVersion" | "delete" | "persist" | "verify" | "blocked";
  remoteWrite: boolean;
  localWrite: boolean;
  reversible: boolean;
  requiresConfirmation: boolean;
  reason?: string;
}
```

JSON 输出必须通过 `docs/schemas/deploy-plan.schema.json`，不得在 TypeScript 与 schema 之间维护两套字段名。

计划按依赖顺序稳定输出，包含环境、账号显示名/脱敏 ID、Worker、D1、migration、assets、预计 mutation 数和恢复点，不含 token。脱敏 ID 固定为 `sha256(rawAccountId).slice(0, 12)`；没有只读授权或无法验证账号时 `verification="unknown"` 且必须省略 `idDigestPrefix`，不能填猜测值。`estimatedRemoteMutations` 必须等于 `remoteWrite=true` 的离散 action 数；每个 action 只表示一次预计远端 mutation。`hasRemoteWrites` 与 `hasLocalWrites` 分别严格派生自 action 集合，不得把本地 state 写入伪装成远端 mutation。`inspect|reuse|verify|blocked` 固定为双只读；`create|acquire|transition|resolve|apply|uploadVersion|activateVersion|delete` 固定为远端 mutation且 `localWrite=false`，全部 `requiresConfirmation=true`；Worker version upload 与 exact-version activation 必须是两个独立 action，禁止退回单体 `deploy` action。只有 `resourceType="localState", action="persist"` 可设置 `localWrite=true, remoteWrite=false`。任何将在确认后写入 `.mallok/state.json` 或本次恢复所必需的 durable local evidence 的命令实例，都必须包含相应 local-state action；一个 action 可代表同一原子恢复 checkpoint 的成组文件写入，但必须在 `reason` 列出固定路径类别。任何包含远端 mutation 的 plan 至少包含一个 `localState/persist` checkpoint；实际 deploy/repair 同时包含 `worker/uploadVersion` 与 `worker/activateVersion`，rollback 只包含后者。`recoveryStrategy` 必须反映本计划写入后的最早持久恢复边界：纯只读 provision 或已完整核实的 deploy no-op 为 `none`，可写/恢复本地 state 的 provision 为 `local-state`，包含远端 mutation 的 deploy 以及 migration/recover/repair/rollback 为 `d1-fence`，T-013 staging cleanup plan 为 `staging-ownership`。deploy 不允许出现 `hasRemoteWrites=false, hasLocalWrites=true` 的含糊计划；本地 state 修复必须进入明确的 provision adopt 或 deployment recover 流程。`--json` 输出必须机器可读。

每个 kind 的最小资源覆盖由 schema 强制：provision 至少含 account+D1；migration 至少含 account+D1+migration+deployment fence；deploy 至少含 account+D1+migration+deployment fence+Worker+assets+health；recover/repair/rollback 至少含 account+D1+deployment fence+Worker+assets+health；cleanup 至少含 account+D1+Worker。没有实际 mutation 的资源仍以 `inspect|reuse|verify|blocked` 明确出现，不能直接从计划省略。runtime validator 还必须拒绝同一 logical resource 的重复语义 action，并证明每个 provider call 恰有一个计划 action。

`kind="cleanup"` 与 `action="delete"` 只为 T-013 的私有 fresh-only staging runner 预留；T-011 不实现公开 cleanup/destroy 命令，也不能用这两个值绕过 T-013 authorization/ownership marker。

dry-run 的定义是零远程 mutation。provision plan 在真实使用时可以在用户已有 Wrangler 身份下执行明确只读的 account/resource inspect；本任务测试不使用该身份，全部由 recording fake 提供。没有只读授权时把远程事实标为 unknown，不能假装已核实。

## 6. `mallok provision`

语法：

```text
mallok provision [--environment <name>] [--adopt-database-id <id>] [--apply] [--yes]
```

- 默认只生成计划；只有 `--apply` 才可能写，非 TTY 同时要求 `--yes`；
- 实际 create/reuse 前按 `CLOUDFLARE.md` 的状态机检查账号/项目/名称、显示计划并确认；
- provision 只创建或显式接管项目 D1，不创建 Worker deployment、不迁移、不设置 secret；
- 每个成功动作立即原子保存恢复状态，支持从中断处继续；
- 同名 D1 无可靠 ownership metadata 时默认阻止；只有 `--adopt-database-id <id>` 显式提供完整 id，经账号/名称/closed database classification 只读验证并确认 plan 才可采用；`--apply` 只原子写本地 state，不产生远端 mutation；无 `--force`；
- plan-only 的 read plan 为 `hasRemoteWrites=false, hasLocalWrites=false, recoveryStrategy="none"`；显式 adopt apply 必须包含 `localState/persist`，为 `false/true/local-state`；create apply 同时包含 `d1/create` 与 `localState/persist`，为 `true/true/local-state`。schema 与 runtime 均需用这三组正例及“把 adopt 谎报为 remote write”的负例验证；
- create 成功但 state 写失败时不自动删除远程资源，只向当前操作者显示一次完整 id 与上述精确 repair 命令；持久日志/证据脱敏。MVP 不自动删除、重命名或清空 D1。

## 7. `mallok deploy`

语法：

```text
mallok deploy [--environment <name>] [--secrets-file <absolute-path>] [--dry-run] [--yes]
```

顺序固定：

1. doctor 与本地 Git ignore/secret 边界检查；
2. 调用 T-008 已验收的 Cloudflare build service，生成或按完全相同 `inputHash` 安全复用 `.mallok/candidates/<inputHash>` immutable snapshot；校验 Worker bundle、snapshot全部文件、build/embedded asset manifest、canonical candidate inventory及其hash与返回摘要，`dist`只作preview且不得进入后续部署；
3. 校验 state、目标 binding 与 generated Wrangler config；
4. 只读分类 remote D1：严格区分 `PRISTINE_UNMIGRATED`、`MALLOK_SCHEMA_V1`、`UNKNOWN_OR_PARTIAL`；
5. 计算 migration/fence/deploy plan，显示目标、baseline version、候选 manifest、恢复点并确认；
6. pristine 实际模式先应用 0001 并验证其原子留下 bootstrap barrier；schema v1 不在 fence 前写远端；
7. 原子 claim bootstrap 或 acquire preflight lease，启动 60 秒 heartbeat；dry-run 只记录 synthetic action，不写 D1；
8. 在 primary 上执行 `doctor --remote --deep`，把 candidate manifest 与全部 current revision refs 分页交叉校验；
9. 原子写入 `.mallok/deployments/<manifest-hash>.asset-manifest.json`、`.mallok/deployments/<inventory-hash>.candidate-inventory.json`和`.mallok/deployments/<lock-id>/wrangler.jsonc`，重读验证canonical bytes/hash/realpath及inventory对snapshot的exact-set覆盖；失败时仍在preflight，按精确id释放；
10. 确认lease未过期、剩余至少600秒，并紧邻CAS重新读取provider active deployment/version：normal必须仍等于baseline，initial必须仍不存在；漂移时释放preflight并重新计划。事实匹配后才原子`preflight -> external, external_stage=ready`；失败不得发出external call；
11. conditional journal `migration_started`，执行已批准migration（如有），核实terminal history后journal `migration_complete`，再验证准确schema/profile与current closure；
12. provider call 前重算 immutable snapshot 全部摘要并再次复核 baseline；生成逻辑 `version_upload_attempt_id` 并以同一 CAS 写 `version_upload_started`。按 `deployment-attempt.schema.json` 先 durable 写新的 request record，再调用项目锁定 Wrangler `versions upload`（只上传、不激活）；每次物理调用使用新的递增 sequence 与 `providerCallId`，同一逻辑 attempt 重传保持 exact candidate/tag/version message。存在 `--secrets-file` 时只传给该非激活 upload；
13. upload 返回或恢复时另行 journal `version-observation`，只接受 exact tag/version message/四 hash 匹配的 canonical lowercase version UUID；结果数组去重升序，非空选最小 UUID，空集才允许重传 upload。把 exact target UUID 与 `version_ready` 以同一 CAS 持久化；未选 inactive version 只保留 evidence，不自动删除；
14. 创建独立 `activation_attempt_id` 并 CAS 到 `activation_started`，durable 写新的 activation request 后调用 `versions deploy <target-uuid>@100% --yes --message <exact-message>`；同一逻辑 activation 的重传只能指向同一 target，每次物理调用仍使用新 `providerCallId`。核实 active target、exact activation message 与 canonical deployment UUID后，CAS 写 `activation_complete + target_deployment_id`；禁止任何上传并立即激活的组合命令；
15. authenticated health 与公开只读 smoke；只有成功后才原子滚动 current/previous snapshot+manifest+inventory 及 version/deployment/attempt evidence、更新 state，并在单个 D1 batch 按精确 id `external -> releasing -> delete`；state 写失败保留 barrier，recover 复核后补写；
16. 任一 provider outcome unknown、进程中断或 target active 但 health 失败时保留 external barrier并返回 `DEPLOY_RECOVERY_REQUIRED`。upload/activation 可按 effect-idempotent exact intent 恢复；terminal-failed 或 active-but-unhealthy deploy target 可在同一 lock 用 repair 换 candidate，不能另开锁。

规则：

- deploy 不隐式 provision；缺 state 返回 `DEPLOY_BLOCKED`；
- deployment preflight 使用 D1 `unixepoch()`，每 60 秒续租；扫描中途过期后旧 id 不能续租/进入 external，必须重新 acquire 并从第一页重扫。external/releasing 无论 TTL 字段如何都保持 hard barrier；不能在通用 finally 中直接删除；
- deploy no-op 必须同时证明：D1 不存在 bootstrap/preflight/external/releasing barrier；local state 与 provider current canonical version/deployment UUID、exact version/activation messages一致；candidate input、candidate inventory、Worker bundle、asset manifest 四个 hash一致；snapshot/manifest/inventory 三份 canonical evidence 存在且 exact bytes 重算一致；migration set一致；authenticated health通过。全部成立才返回`COMPLETE`，fence/Wrangler/state滚动调用数均为0；缺一项就不得仅凭本地 hash 跳过；
- 全新 D1 只有在 state/binding/name 匹配，且只读 schema 检查证明除批准的 provider metadata 外完全 pristine、migration history 为空时才可进入 initial migration；存在任意未知/部分 user object 时返回 `DATABASE_SCHEMA_INCOMPATIBLE`，不得自动 adopt；
- deploy 总是调用 T-008 已验收的 build service；只有 candidate 的规范 input hash 与本次 config/content/theme/public/asOf/toolchain 完全一致时才可复用，否则重新本地构建。构建失败属于 `NO_REMOTE_CHANGE`，且发生在任何 migration/deploy 前；
- 本任务只能编排既有 build service，不得在 deploy 目录复制或修改 BuildWriter、主题 renderer、Worker bundler、media 提取器或 manifest/hash 规则，也不得在 build service 之外补写 candidate；
- `--dry-run` 零远程写；非 TTY且非CI的真实动作必须`--yes`并禁止交互；`CI=1`的Cloudflare infrastructure mutation即使带`--yes`也以8拒绝，plan/dry-run仍可用；
- subprocess 只允许项目本地、已锁定 Wrangler；参数以数组传递，不经 shell 拼接；
- dry-run 必须使用 Wrangler 本地支持的 dry-run/bundle 能力，禁止调用 deploy/migration remote 命令；
- secret 值不在 argv/config/state；deploy 不调用 `secret put`。无 `--secrets-file` 时 doctor 按 required-secret 契约检查远端是否存在；首次部署可显式给项目外 secrets file，严格验证普通文件/symlink/owner/mode、无 BOM UTF-8 单行、唯一 key 和 canonical token 后，仅把 path 参数传给非激活的 `versions upload`，activation 不再读取它；绝不把值读出到日志、plan/evidence，也不删除用户文件；
- remote deep audit 按 DATABASE/CLI 固定为每页最多 50 个 current pointer、总时限 300 秒；除 codec/hash/tag/payload 外，逐项要求 candidate manifest 包含 current asset URL；缺失返回 `DEPLOY_ASSET_CLOSURE_FAILED`，同 URL hash 变化允许；超时/中断返回 `DOCTOR_AUDIT_INCOMPLETE`，并安全释放仍处 preflight 的 lease。进入 external 后任何不确定性都保留 barrier。同步 `/health` 仍保持有界且允许合法 fence 存在，不能拿它替代 deep audit；本任务用 recording fake 验证分页、取消与时限，不访问真实 D1；
- 失败状态精确分类 `NO_REMOTE_CHANGE`、`DEPLOY_LOCK_HELD`、`DEPLOY_LOCK_LOST`、`MIGRATED_NOT_DEPLOYED`、`DEPLOYED_HEALTH_FAILED`、`DEPLOY_RECOVERY_REQUIRED`、`COMPLETE`；数据库不自动回滚；
- cloudflare candidate/asset manifest和candidate inventory在build service中产生；成功deploy后把 exact canonical lowercase active Worker version/deployment UUID、独立 version-upload/activation operation+attempt、candidate input/inventory hash、bundle hash、snapshot/manifest/inventory evidence path原子滚动到current/previous state。普通 deploy 的两个 operation id 同为当前 lock id但两个 attempt 必须不同；rollback 保留目标 version 的原 upload pair，并用当前 rollback lock/activation attempt 记录新激活；
- per-lock attempt journal 固定为 `.mallok/deployments/<lock-id>/attempts/<6位sequence>-<provider-call-id>.request|result.json`。request 必须在调用前以 exclusive temp+fsync+rename durable 落盘，result 仅在 terminal 后 exclusive-create；旧记录永不覆盖。request/result 的 lock/attempt/call/sequence/operation/purpose/四hash/tag/message/target 必须匹配，孤立 result、重复 sequence/call id 或字段漂移 fail closed；`version-upload|version-observation` 绑定 `version_upload_attempt_id`，`activation` 绑定 `activation_attempt_id`；
- 实现`mallok deployment recover/repair/rollback`：recover按 stage 和 immutable journal resume exact intent；upload outcome unknown 先用同 logical attempt/new providerCallId 做 version observation，空集才重传非激活 upload；activation outcome unknown 只可重传 exact target。repair仅用于`purpose=deploy`，且只接受三种完整证明：upload terminal-failed后完整version-observation success为空；同logical activation的每份request都有terminal-failed result、无缺result且active仍为baseline/initial-none；或target active但health失败。满足其一才可同锁CAS retarget新candidate、清空两个attempt/target/deployment并回到`migration_complete`；若旧target已active则设为新baseline。normal deploy另支持显式`recover --abort-to-baseline --apply`：仅active精确等于baseline、非initial、尚无activation request或每份request都有terminal-failed result且无缺result、migration向后兼容且closure/ledger通过时，保留既有immutable request/result与audit判据后释放；不创建未定义的新evidence格式，initial没有baseline时不能abort。rollback必须显式canonical target version UUID，无barrier时获取rollback fence并直接写`version_ready`，只执行activation；同锁retarget清空activation attempt/deployment并回到`version_ready`，health失败只能再次显式rollback，不能repair。三者都验证snapshot/manifest/inventory/tag/messages/current closure，不得调用默认rollback、单体deploy或另开第二把锁；
- logs/错误对 token、account/database id、绝对路径做脱敏，但确认界面必须让操作者能辨认目标。

## 8. 可测试的副作用端口

Cloudflare 命令、文件状态、确认输入和 clock 全部通过注入端口。测试使用 recording fake 验证：

- dry-run 远程 mutation 调用数为 0；
- 缺确认、`CI=1` infrastructure mutation、unknown ownership 均为0；CI即使有`--yes`也不得调用remote port；
- state 缺失时 doctor 只输出候选与 adopt repair 命令而不写文件；adopt plan/apply 的远端 mutation 为 0，且只有 apply+确认原子重建匹配当前 projectId 的 state；
- 精确 argv 顺序、项目本地 Wrangler 路径和 redaction；
- 每个步骤故障后的 state/recovery；
- migration/deploy 失败不写虚假 deployment/asset registry；
- preflight acquire/renew/expiry、普通/initial takeover、external前baseline漂移、bootstrap claim、`ready/migration_started/migration_complete/version_upload_started/version_ready/activation_started/activation_complete`逐点崩溃、provider outcome unknown、resolve response loss与错误lock id均有状态机测试；request 已落盘但 subprocess 未启动、upload 迟到/重复成功、observation 空/单个/多个匹配、activation 重传、attempt A→B→A、terminal-failed同锁retarget、normal abort-to-baseline、initial abort拒绝、repair deploy-only、rollback同锁回`version_ready`/二次rollback也必须覆盖；external永不因clock前进自动放行；
- attempt journal schema与runtime聚合测试覆盖 request/result correlation、observation绑定upload attempt、UUID确定性最小选择、孤立/重复/partial记录、不同logical attempt与每次fresh providerCallId；必须加入同一version attempt在upload/observation间漂移candidate/hash/tag/message、同一activation attempt漂移purpose/hash/tag/message/target的跨文件反例，并证明全部在provider call前fail closed；DeployPlan测试覆盖 remote→local persist、uploadVersion→activateVersion依赖序、rollback activation-only、adopt local-only 与乱序反例；
- candidate manifest 缺 current asset 时 migration/deploy 调用数为 0；secrets file 内容不进入 recorded argv/log（只有经边界验证的 path）；
- pristine first-deploy recording fake必须证明顺序为classify→confirm→initial migration+bootstrap barrier→schema/empty-set recheck→claim initial preflight→closure→external→non-activating upload→version observation→persist target→exact activation→health→resolve；claim后过期/崩溃可在DB空且无active Worker时takeover；partial/unknown DB的migration/upload/activation/fence调用数为0；
- 并发build替换`dist`不能改变recorded Wrangler读取的snapshot bytes；snapshot任一文件漂移、symlink或per-lock config指向`dist`时external call为0；
- 首次部署target active但health失败时repair沿用exact lock并可retarget新candidate；target/outcome事实不完整时remote调用为0且barrier保留；

- rollback recording fake 验证显式 version、manifest/tag/closure/schema；缺 evidence、默认 rollback、outcome unknown 均为零 version switch；
- provision 不包含任何 delete/destroy 调用。

## 14. 停止条件

- dry-run、doctor 或 plan 会认证、联网或修改远程状态；
- deploy 会隐式创建资源或使用全局 Wrangler；
